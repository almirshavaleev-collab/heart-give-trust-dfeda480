
# Локализация ПДн донора (email + ФИО) — сравнение вариантов

Контекст: внутренняя политика, без строгой проверки РКН. ПДн в проекте — только `donor_email`, `donor_name`, `donor_phone` в `donations`, и `email`/`full_name`/`phone` в `profiles`. Это сильно упрощает задачу — полная замена БД не нужна.

---

## Вариант A — Шифрование ПДн в Supabase + ключ в РФ (рекомендую)

Никакой второй БД. ПДн физически продолжают лежать в Supabase, но в зашифрованном виде; ключ шифрования хранится на VPS в РФ и выдаётся Edge Function по запросу. Без ключа в Supabase лежит «непригодный к идентификации набор байт».

```text
Frontend ──► Edge Function ──► RU Key Service (VPS, РФ)
                  │                    │
                  ▼                    ▼
         Supabase (ciphertext)   ключ AES-GCM
```

- Меняется: добавляются колонки `donor_email_enc`, `donor_name_enc`, удаляются plaintext-колонки. Edge Functions расшифровывают на лету для админки и писем.
- Auth: остаётся Supabase. `auth.users.email` — отдельный вопрос (см. ниже, опция).
- Сложность: **3/10**. 3–5 дней.
- Плюсы: минимум инфраструктуры, Realtime/RLS/миграции работают как раньше, нет двух источников правды.
- Минусы: формально email всё ещё «находится» в Supabase, но в нечитаемом виде — для «внутренней политики» этого обычно достаточно. Поиск/фильтрация по email в админке требуют расшифровки на бэке.

Опция A+: дополнительно перевести Supabase Auth на свой Keycloak/Ory в РФ через 3rd-party JWT — тогда и `auth.users` уходит из управляемого Supabase. Это ещё +7–10 дней.

---

## Вариант B — RU outbox для ПДн, Supabase хранит только ID

Поднимаем минимальный PostgreSQL + REST-API на VPS в РФ. Frontend пишет ПДн туда, Supabase хранит только `donor_ref` (UUID). Edge Function подтягивает email/имя из RU при отправке писем и в админке.

```text
Frontend ──► RU API (VPS, РФ) ──► RU Postgres (ПДн)
     │              │
     │              ▼ outbox events
     ▼         RU worker ──► Supabase (donor_ref, amount, status)
Supabase ◄── Edge Function запрашивает ПДн по ref
```

- Меняется: новый сервис, RU-схема, миграция существующих записей, переписывание `create-payment`/`yookassa-webhook`/`process-recurring-payments` чтобы ПДн шли в RU. Админка получает ПДн через прокси.
- Auth: остаётся Supabase (`auth.users.email` всё равно вне РФ — частичное решение).
- Сложность: **7/10**. 3–4 недели + ежемесячная эксплуатация VPS, мониторинг очереди.
- Плюсы: ПДн действительно живут в РФ, чёткая граница.
- Минусы: лаг при отправке писем (+200 мс), двойные миграции, нужен DBA-навык, расходы на VPS/мониторинг, Realtime по ПДн невозможен.

---

## Вариант C — Полная двойная БД (RU master → Supabase replica)

То, что описано в исходном вопросе: RU Postgres — мастер всего, Supabase — реплика для фронта.

- Сложность: **9/10**. 1.5–2 месяца + постоянная эксплуатация.
- Плюсы: максимально соответствует букве 152-ФЗ при условии замены Auth.
- Минусы: двойные миграции, конфликты схем при обновлениях Lovable, риск рассинхрона, дорого. **Не оправдано для внутренней политики и 2 полей ПДн.** Включил для полноты картины.

## Рекомендация

Для заявленной цели («внутренняя политика, на будущее», только email + ФИО) — **вариант A**. Если со временем потребуется усилить — добавить A+ (свой Auth) или мигрировать на B без отказа от текущего фронта.

## Что делать дальше

Если выбираете A, следующий шаг — план реализации:
1. Добавить колонки `*_enc` и миграция существующих `donor_email`/`donor_name`.
2. Поднять минимальный KMS-эндпоинт (Node/Go на VPS, AES-GCM, ключ в памяти + бэкап в Vault).
3. Шифрование/расшифровка в `create-payment`, `yookassa-webhook`, `send-transactional-email`, `request-donation-link-code`, админских RPC.
4. Поиск в админке — через сервер-сайд расшифровку + bcrypt-индекс по email для поиска по точному совпадению.
5. Удалить plaintext-колонки после миграции.
